## cron スロット選びのガイド

GitHub Actions の scheduled workflow は best-effort UTC で発火します。
公式 docs にも「高負荷時には遅延しうる」と書かれていますが、
どれくらい遅延するかは書かれていません。

コミュニティで広く言われている目安:

- 通常(off-peak slot): 数分〜十数分
- 混雑時間帯(米国・欧州が両方アクティブな UTC 14:00–19:00 帯): 30 分〜1 時間超
- 最悪ケース: 数時間 / その回はスキップ

正確な数値は GitHub のインフラ状況や時期で変動するので「だいたい」として
読んでください。自分のリポジトリでの実遅延は [後述の確認コマンド](#自分の遅延を測る) で
測定できます。

このページは、混雑しにくい UTC slot を選ぶための実用ガイドです。

### TL;DR

- UTC `:30` マークの方が `:00` より遅延が少ない傾向
  (`:00` は世界中で大量に設定されてるため queue が詰まる)
- 米国と欧州の業務時間が両方ある UTC 帯は遅延しやすい
  特に UTC 14:00–19:00 は混雑ゾーン
- UTC 22:00 〜 08:00 が穏やかなウィンドウ
  (米国 EOD → 欧州 起床までの隙間)
- workflow を更新した直後 ~15 分はスケジューラが新 cron を認識
  する前で、最初の fire はスキップされやすい

### スロット選定の考え方

| slot(UTC)| 現地時間(対応)| グローバル状況 |
|---|---|---|
| 14:00–19:00 | EDT 10:00–15:00 / PDT 07:00–12:00 / CET 16:00–21:00 | 米国 + 欧州が両方アクティブ(混雑ゾーン)|
| 22:00–08:00 | EDT 18:00–04:00 / PDT 15:00–01:00 / CET 00:00–10:00 | 米国 EOD → 欧州 起床までの隙間(穏やか) |

本サンプルリポジトリは UTC 22:00 (JST 07:00) を採用しています。

## なぜ peak UTC slot が悪いのか

GHA の scheduled workflow キューは全 GitHub で共有されており、
米国・欧州の業務時間中は混雑します。

UTC 14:00–19:00 は米国(EDT 業務時間中・PDT 始業)と欧州(CET 業務終盤)の
業務時間が重なる帯。一方 UTC 22:00–08:00 は米国 EOD 後・欧州 就寝中で、
グローバルに最も穏やかなウィンドウ。

`:00` マークは「毎時0分」設定が世界中で大量にあるため、さらに混雑します。
`:30` の方が空いている傾向。

### 個人運用で観察された遅延の傾向(参考値)

個人でいくつかの cron workflow を実運用してきた範囲での体感です。
具体的な数値はその日の GitHub インフラ状況で大きくぶれるので、
order(分単位の桁感)として読んでください。

| slot | JST | 観察された遅延の傾向 |
|---|---|---|
| UTC 22:00 帯(本テンプレデフォルト) | JST 07:00 | おおむね 数分〜30 分台 に収まる。たまに 1 時間近くまで延びる日もあり |
| UTC 17:30 帯(peak の入り口) | JST 02:30 | 1 時間超 になることもしばしば。スキップされた回もあり |
| UTC 14:00–19:00(peak ど真ん中) | JST 23:00–04:00 | 1 時間超 が常態。最悪ケースで数時間 / 回をスキップ |

つまり off-peak と peak で 体感の遅延が数倍違う、というのが運用してみた
感触。JST 朝の時間に動かしたいなら UTC 22:00 帯がコスパ最良。

### 実用ガイドライン

1. 自分の希望時刻を UTC に変換する
2. UTC 14:00–19:00 を避ける
3. `:30` を `:00` より優先
4. workflow 変更を push してから次の scheduled fire まで 15分以上
   間隔を空ける(or 手動 dispatch で先に動作確認する)
5. `workflow_dispatch:` を必ず on に残しておく
   (cron がスキップされても即時手動で発火できる)

### 自分の遅延を測る

deploy 後、fire 時刻をチェック:

```bash
git log origin/main --author="github-actions" \
    --pretty=format:"%h | %ai | %s" -10
```

`%ai` の timestamp は UTC。cron のスケジュール時刻から引けば、
自分のスロットの遅延分布が出ます。

### 注意点

- GHA は 60 日以上 commit のない repo の scheduled workflow を
  勝手に停止します。動かなくなったと思ったら commit を1個入れて再起動を
- 無料枠の private repo は public repo と同じスケジューリングプールを
  使う(private/public で遅延プロファイルは変わらない)
- GitHub のインフラ変化で将来は混雑パターンが変わる可能性あり
